# ICS Mongolia Website — Improvement Plan

This folder tracks a multi-session effort to improve icsmongolia.com. It's designed to be
picked up cold — by you or by Claude — after any length of gap.

**How to resume:** read `LOG.md` (last entry = what happened most recently and what's next),
then come back here and take the next `⬜ Not started` item in priority order, skipping
anything `⏸ Blocked`.

**Status legend:** `⬜ Not started` · `🔵 In progress` · `✅ Done` · `⏸ Blocked (needs input from you)`

**Ground rules (from the repo's CLAUDE.md):**
- Never edit `en/index.html` / `mn/index.html` content directly — they're generated by
  `npm run build` from `content/en.yml` / `content/mn.yml`. Structural changes (new sections,
  new meta tags not driven by YAML) go in the raw HTML + a matching `build.js` selector if the
  content should become CMS-editable later.
- Run `npm run build` after any YAML edit, and the local-asset-reference checker (see repo
  CLAUDE.md) before calling a session done.
- This plan folder is excluded from the deployed site via `.assetsignore` — safe to keep
  detailed working notes here without shipping them.

## Phase 1 — Foundation (technical, no decisions needed)

Self-contained, no content or approvals required. Good default phase to work through first.

- ✅ **Open Graph / Twitter meta tags** — added `og:title`, `og:description`, `og:image`
  (1280×720, the hero photo), `og:url`, `og:locale`(+alternate), `twitter:card` to
  `en/index.html`, `mn/index.html`, and a lighter set on the root redirect `index.html` (for
  crawlers that read meta before following the JS/meta-refresh redirect).
- ✅ **`robots.txt` + `sitemap.xml`** — added at repo root, listing `/`, `/en/`, `/mn/` with
  hreflang alternates, `Sitemap:` line in `robots.txt`.
- ✅ **`schema.org` Organization JSON-LD** — added to both language pages (name, logo, url,
  description, both founders as `ContactPoint`s). No street address available, so `address`
  was left out rather than invented — see Not yet specified if that becomes available later.
- ✅ **Proper favicon** — old favicon/apple-touch-icon pointed at `ics-fod-logo.png` (the AI
  product mark, not the company logo). Cropped the hexagon icon out of `images/ics-logo.png`
  with `sharp` and generated `images/favicon-32.png`, `favicon-192.png`, `favicon-512.png`
  (transparent bg) and `images/apple-touch-icon.png` (180×180, white bg for iOS). All three
  HTML entry points now reference the new set.
- ✅ **Image compression** — installed `sharp` temporarily (`npm install --no-save`, removed
  after use — not a persisted dependency) and generated WebP versions:
  `control-room-mining-site.jpg` 204 KB → `.webp` 92 KB (-54%),
  `ics-fod-product.png` 380 KB → `.webp` 34 KB (-91%). Wired in via `<picture><source
  type="image/webp">` + original `<img>` fallback in both language pages. **Known limitation:**
  if the `image`/`product.image` fields in `content/en.yml` / `content/mn.yml` are ever changed
  via the CMS, `build.js` will update the `<img>` fallback `src` but *not* regenerate the
  sibling `.webp` — the `<source>` would go stale. Fine for now since these two images are
  static; flagged here so a future session doesn't get surprised.
- ✅ **Preload hero image** — added `<link rel="preload" as="image" type="image/webp"
  fetchpriority="high">` for the hero WebP in both language pages' `<head>`.
- ✅ **Alt-text / accessibility pass** — audited during this session: every `<img>` already had
  meaningful `alt` text (driven by `image_alt`/`logo_alt` fields in content YAML). No changes
  needed.

**Verification run this session:** `npm run build` (clean), the CLAUDE.md local-asset-reference
checker (`local refs ok`), JSON-LD parsed with `JSON.parse` (valid on both pages), `node --check
script.js` (OK), local `python3 -m http.server` smoke test (`/`, `/en/`, `robots.txt`,
`sitemap.xml`, the new `.webp` all returned 200).

## Phase 2 — Analytics

- ❓ **Pick an analytics provider, then wire it up.** Recommendation: **Cloudflare Web
  Analytics** — free, no cookie banner needed (privacy-friendly, no client-side cookies), and
  it's a natural fit since the site already deploys via Cloudflare Workers on Badraa's account.
  Alternative if you'd rather have fuller dashboards: Plausible (paid) or GA4 (free, but needs
  a cookie/consent notice for EU-style compliance — probably not a real concern for a
  Mongolia-focused audience, flagging for completeness).
  - ⏸ Blocked on: (a) you confirming the provider (default assumption: Cloudflare Web
    Analytics), and (b) someone with access to Badraa's Cloudflare account completing the
    dashboard-side signup step below.

  **Ready-to-execute checklist (Cloudflare Web Analytics path), once unblocked:**
  1. In Badraa's Cloudflare dashboard: **Analytics & Logs → Web Analytics → Add a site**,
     enter `icsmongolia.com`. Cloudflare hands back a JS beacon snippet, e.g.:
     `<script defer src='https://static.cloudflareinsights.com/beacon.min.js'
     data-cf-beacon='{"token": "..."}'></script>`
  2. Paste that token/snippet here in this doc (or send it to me) — it's a public client-side
     token, not a secret, safe to store in this repo.
  3. I add the snippet to `en/index.html`, `mn/index.html`, and the root `index.html` (raw HTML
     edit, same pattern as the Phase 1 meta-tag work — not YAML-driven, so no `build.js` or
     `content/*.yml` changes needed).
  4. Rebuild, run the same verification pass as Phase 1 (asset-ref checker, `node --check
     script.js`, local smoke test), commit, push.
  5. Confirm in the Cloudflare dashboard that traffic starts appearing after the next real
     visit (may take a few minutes to show up).

  If GA4 is chosen instead: step 1 becomes creating a GA4 property + data stream for
  `icsmongolia.com` in Google Analytics, which yields a `G-XXXXXXX` measurement ID; steps 2-5
  are the same shape but with the `gtag.js` snippet instead, plus a decision on whether a
  cookie-consent banner is wanted.

## Phase 4 — Structural (needs scope decisions)

- ❓ **Dedicated ICS-FOD product page** (`/products/ics-fod/` or similar) — the product has
  real specs (<1s latency, 24/7 monitoring, deep-learning vision) currently compressed into
  three feature cards on the homepage. A dedicated page could target search intent like
  "foreign object detection mining Mongolia" directly, and host a datasheet/demo video if one
  exists. Needs a scope decision: worth the structural change now, or later once there's a demo
  video/datasheet to anchor it?
- ❓ **Contact form vs. current mailto links.** Current contact section is just names + emails
  + phones. A real form lowers friction but needs a submission backend — options: (a) a small
  Cloudflare Worker endpoint (fits the existing stack, no third-party dependency), or (b) a
  third-party form service (Formspree etc., needs an account signup). Recommendation: (a),
  since the site is already a Cloudflare Worker — no new account/dependency needed.
- ❓ **Blog / news section** — helps SEO and signals an active company, but only worth doing if
  someone will actually post to it periodically. Needs a decision on whether that commitment
  exists before building the scaffolding.
