# Handoff — ICS Mongolia website improvement effort

Read this first in a brand-new session. It's the orientation doc; `PLAN.md` and `LOG.md` are
the living tracker underneath it. This file itself is static — update it only if the *shape*
of the effort changes (new phase structure, new tracking convention), not for routine progress
(that goes in `LOG.md`).

## What this is

A multi-session effort to improve icsmongolia.com (live company site for Industrial Control
Solutions LLC, a Mongolian mining-automation company). Started because the user asked for
improvement suggestions, then asked to track implementation across sessions/days instead of
doing it as a one-shot. No external issue tracker is used — tracking is two markdown files in
this folder, git-tracked but excluded from the deployed site.

## How the tracking system works

- **`PLAN.md`** — the stable task list. Phases, each item tagged with a status emoji (⬜ not
  started / 🔵 in progress / ✅ done / ⏸ blocked / ❓ needs a decision from the user). Has a
  "Decisions made so far" index at the bottom (one line per resolved thing, linking to the
  `LOG.md` entry with detail) and an "Out of scope" section. Edit this in place as status
  changes — it's not append-only.
- **`LOG.md`** — append-only session log, **newest entry on top**. Each entry: date, what got
  done, what's next. This is what a cold session should read *first* to know where things stand
  — `PLAN.md` alone doesn't tell you *why* something is blocked or what was just tried.
- **Resume procedure** (already stated at the top of `PLAN.md`): read `LOG.md`'s top entry, then
  go to `PLAN.md` and take the next `⬜`/ready item in priority order, skipping anything `⏸`
  unless you're the one unblocking it.
- Every session that does real work should: update `PLAN.md` status markers, append a `LOG.md`
  entry, and — **only when the user explicitly says to** — commit and push. Never commit/push
  unprompted; this repo auto-deploys on push to `main`, so a push is a live-site action.

## Ground rules (carried over from repo CLAUDE.md, restated because they're load-bearing here)

- **Never hand-edit `en/index.html` / `mn/index.html` content** — they're generated by
  `npm run build`. Exception: structural changes not driven by YAML (new `<head>` tags, wrapping
  `<img>` in `<picture>`) are safe to hand-edit directly, because `build.js` only touches
  specific body text nodes/attributes via `querySelector` — verified this by grep before relying
  on it. If you add a new YAML-driven field, add the matching `build.js` selector too.
- **Run `npm run build`** after any `content/*.yml` edit, and the local-asset-reference checker
  (command is in repo `CLAUDE.md`) before calling a session done.
- **Never fabricate facts.** Case-study results, testimonial quotes, a street address, client
  names — anything requiring real-world facts not already in the repo must be left blocked
  (⏸ in `PLAN.md`) pending real input from the user/team, not invented. This mirrors the
  platform-level rule against fabricated records/reviews/testimonials.
- **Mongolian copy is placeholder-quality** per the repo's own `CLAUDE.md` — treat any MN text
  you produce as machine-quality unless a native speaker (Badraa or Ider) has reviewed it, and
  say so explicitly rather than presenting it as final marketing copy.
- **Concurrent edits happen.** The site has a live Cloudflare Pages CMS that commits directly to
  `origin/main` independently of agent sessions (real content edits by the team, not you). A
  `git push` can get rejected mid-session for this reason — see `LOG.md`'s Phase 1 entry for the
  exact fetch → inspect-diff → merge → rebuild → re-verify → push sequence that handled it
  safely. Always inspect the incoming diff before merging blindly (to separate real content
  changes from YAML line-wrap noise), and always re-run `npm run build` after merging, since
  merged YAML changes need to be re-baked into the HTML.
- Get explicit user confirmation before any `git commit`/`git push` on this repo.
